# Delivery contract

Deliver only after CAD review, Blender review, and cross-software review meet their gates. Use `assets/templates/delivery-report.json` and include: accepted revisions, an explicit immutable `manifest_lineage`, hashes for every Manifest/deliverable/evidence/review path, read-back evidence, review outcomes, residual assumptions/limitations, reproduction/opening instructions, and any required human/licensed review.

Contract 3.0 publishes an immutable snapshot with `python scripts/publish_delivery.py <validated-source-report> --project-root <project-root> --release N`. The publisher refuses every existing `delivery/accepted/rN`, copies accepted evidence while preserving relative paths, recalculates SHA-256, emits `delivery/delivery-report-rN.json`, `delivery/final-hash-ledger-rN.json`, and `delivery/package-rN.zip`, validates the new release, and then creates non-overwriting FCStd/blend copies under `working/`. For rN after r1, the adjacent prior report must exist, the source Delivery Report revision must increase, accepted revisions may not regress, and at least one formal CAD or Blender Stage Result revision must increase. Repackaging stale evidence as a new release is rejected. Validate the published report with `python scripts/validate_delivery_report.py delivery/delivery-report-rN.json --project-root <project-root>`.

The report's artifact paths are relative to its declared `delivery/accepted/rN`; the validator never resolves them against stage directories or `working/`. Contract 3.0 requires the exact rN outer ledger and formal evidence-contract Stage Results. Windows read-only attributes on accepted files are only an operator warning. Hash comparison is the integrity control. The ZIP is excluded from its own ledger because it contains that ledger, but the validator still opens it and requires its members and contents to exactly match the accepted snapshot, report, and ledger.

Historical Stage Results and reviews must cite the Manifest revision they actually consumed. That revision may be older than the final active Manifest, but it must occur on the verified parent chain leading to the final revision. Never rewrite historical evidence to claim it consumed a future Manifest.

New deliveries declare Blender geometry fidelity and the render QA profile. `envelope_proxy` limitations must say that it is a proxy and not face-accurate/final presentation geometry; `exact_mesh` requires stricter dimension and topology evidence. Use the outer ledger protocol in [hash-ledger](hash-ledger.md): the report never hashes itself or the ledger, and the ledger hashes the finalized report while excluding itself.

Routine publication creates FCStd/blend working copies only from files inside the newly accepted snapshot; unaccepted stage models are not candidates. The historical migration helper may explicitly use existing edited project models as working-copy source while independently restoring accepted/r1 from the verified ZIP.

Distinguish static schema/script validation from live CAD or Blender verification. Never claim fabrication readiness, code compliance, engineering sign-off, FEA/CFD validation, or live end-to-end operation without corresponding evidence and authority.

For `exact_mesh`, export a CAD and Blender `canonical_mesh` JSON using `assets/templates/canonical-mesh.json`. Partition vertices and faces by controlled `object_id`; the object ID set must exactly equal the consumed Manifest. Delivery validation recomputes per-object and aggregate vertices, edges, faces, connected components, and geometry digests from those files; it also reads the hash-bound CAD and Blender snapshots to recompute controlled measurements. Cover every controlled object's critical dimensions plus each declared transform, parent, and topology check. Self-reported counts, digests, measurements, or a boolean topology claim are not evidence.

Render QA requires fully decodable PNG files and one hash-bound camera metadata JSON per image. Metadata binds the image path/hash, camera, projection, 4x4 view matrix, render dimensions/engine, subject-frame fraction, excluded collections, and output role. Require exactly one clearance image and one presentation image. Process evidence uses `assets/templates/process-log.json`; its project, stage, packet, attempt, canonical command digest, artifact path/hash set, exit code, and exact writer/readback event sequence are validated before Stage Result promotion.
